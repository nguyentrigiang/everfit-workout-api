# Decisions

Decisions made with the user during planning. Feeds the README "design decisions / trade-offs" section.

## 2026-10-07 — ORM
- Decision: Prisma.
- Alternatives: TypeORM (closest to Eloquent, official @nestjs/typeorm), Drizzle (SQL-like, typed).
- Why: Fast setup, generated migrations, strongest type-safety. Heavy aggregation / pagination queries are written as raw SQL with `$queryRaw` tagged templates (bind parameters) for full control over query plans and indexes.

## 2026-10-07 — Database for e2e tests
- Decision: A separate test database (`everfit_test`) on the same Postgres container in docker-compose.
- Alternatives: Testcontainers (fresh container per run).
- Why: Simple and fast, no extra dependency. Trade-off: tests share a long-lived DB, so each test uses its own userId and the suite resets tables before running.

## 2026-10-07 — Startup behavior of `docker compose up`
- Decision: The app container runs `prisma migrate deploy` (and the exercise seed, once it exists) automatically before starting.
- Alternatives: Manual migration/seed commands documented in README.
- Why: The assignment requires setup to work with `docker compose up`; reviewers get a working API with one command. The 50k-entry performance seed stays a separate command.

## 2026-10-07 — API documentation
- Decision: Swagger (OpenAPI) UI at `/docs`, generated from DTOs; README summarizes endpoints and error codes.
- Alternatives: README only.
- Why: Docs stay in sync with validation rules, and the video demo can use Swagger UI.
- Implementation (2026-10-08): the `@nestjs/swagger` CLI plugin derives request schemas from the existing DTOs (types, validators, doc comments), so validation and docs are not written twice; responses are documented with real JSON examples per status rather than response classes (faster, readable; trade-off: response schemas are less strict for client generation). Enabled in every environment for this assignment; a real deployment would gate it behind an env flag.

## 2026-10-08 — Test runner
- Decision: Vitest (+ Supertest for e2e), as generated by NestJS 12.
- Alternatives: Jest (default in NestJS ≤ 11).
- Why: The project is ESM (`"type": "module"`); Jest's ESM support is still experimental and needs extra configuration, while Vitest supports ESM and TypeScript out of the box and is faster. The API is nearly identical to Jest. Known risk: if Nest DI fails in tests due to missing decorator metadata, add the SWC plugin (`unplugin-swc`).

## 2026-10-08 — Environment validation
- Decision: Validate env vars at startup with class-validator / class-transformer via `ConfigModule.forRoot({ validate })`; the app fails fast with a clear message.
- Alternatives: Zod, Joi.
- Why: class-validator is needed for request DTOs anyway, so one validation library serves the whole app with no extra dependency.

## 2026-10-08 — Logging
- Decision: Structured logging with nestjs-pino. JSON output in production/Docker; pino-pretty (dev dependency) for local development. Every HTTP request is logged once (method, url, status, response time, requestId) without request/response bodies. Request id comes from the `x-request-id` header or is generated (UUID) and echoed back.
- Alternatives: JSON everywhere; logging bodies; logging errors only.
- Why: JSON logs are machine-parseable for log aggregation; pretty logs keep local work and the video demo readable. Not logging bodies keeps log volume low (bulk requests can be large) and avoids leaking user data.
- Note: The request URL is logged with its query string. Query params here are filters (exercise name, date range, unit), not sensitive data, and they are needed to debug slow or failing list queries. Revisit if sensitive params are ever added.
- Note: `NODE_ENV` defaults to `production`, so a missing value never tries to load dev-only tooling (pino-pretty is a dev dependency).

## 2026-10-08 — Error responses
- Decision: Every error uses one shape: `{ statusCode, code, error, message, details, path, timestamp, requestId }`. `code` is a stable machine-readable string (e.g. `VALIDATION_ERROR`, `NOT_FOUND`), `error` is the HTTP reason phrase. Unparsable JSON currently returns `BAD_REQUEST` (dedicated code tracked as backlog item B1). Validation errors return 400 with `details: [{ field, message }]`, where `field` is the full path into nested payloads (e.g. `entries[0].sets[2].weight`). Pipe and filter are registered through DI (`APP_PIPE`, `APP_FILTER`) so e2e tests run the same pipeline as production. 5xx responses never expose internals (message and details are masked for every exception type); the stack is only logged. Statuses without a dedicated code fall back to `BAD_REQUEST` (4xx) or `INTERNAL_ERROR` (5xx) so the code table stays fixed.
- Alternatives: no `code` field; 422 for validation errors; field name only in details.
- Why: Clients can branch on `code` instead of parsing messages, and the README can document a fixed error-code table. 400 is the NestJS default and what clients expect. Full paths tell a coach exactly which set in a bulk request is wrong.

## 2026-10-08 — Database: PostgreSQL
- Decision: PostgreSQL 18 (latest stable; upgraded from an initial default of 16 before any data existed).
- Alternatives: MongoDB.
- Why: The workload is relational and aggregation-heavy. PR queries are top-1 lookups per user + exercise that map directly onto composite B-tree indexes; history filters join a small exercise catalog; bulk logging needs transactions and unique constraints. MongoDB's flexible schema is not needed (fixed data shape), and nested sets would need `$unwind` for PR queries. Version 18 over 16: supported until 2030 (vs 2028), native `uuidv7()`, B-tree skip scan and async I/O; there is no existing production cluster to match. 19 is still in beta.

## 2026-10-08 — Time and timezone
- Decision: Clients send `date` as an ISO 8601 datetime with offset (e.g. `2026-10-07T07:30:00+07:00`); it is required. Stored as `performed_at` (`timestamptz`, UTC) plus `local_date` (`date`, the client's calendar day) and `utc_offset_minutes`. Calendar questions ("PR this month vs last month") use `local_date`; ordering, pagination and time ranges use `performed_at`.
- Alternatives: date + IANA timezone; date only treated as UTC.
- Why: Unambiguous with no timezone database lookup. Date-only UTC would put a 6am workout on the 1st (UTC+7) into the previous month. Trade-off: the offset is a snapshot, not a timezone rule, so we cannot re-derive local time under a different DST rule (not needed here).

## 2026-10-08 — Sets storage and PR strategy
- Decision: Sets live in their own table `workout_sets`, one row per set. Each set stores the original `weight` + `unit` and precomputed `weight_kg`, `volume_kg` (reps × weight_kg) and `e1rm_kg` (Epley). `user_id`, `exercise_id`, `performed_at` and `local_date` are copied from the entry onto each set so PR queries (including calendar-range comparisons) need no join. Composite indexes `(user_id, exercise_id, <metric> DESC)` make each PR a single index lookup; `(user_id, exercise_id, local_date)` serves range comparisons. Normalized kg metrics are `numeric` with 6 decimals so lb→kg conversion is not rounded at write time (rounding only on output). Hand-written CHECK constraints (`reps > 0`, `weight >= 0`, offset range) back up request validation.
- Alternatives: JSONB array of sets on the entry; computing metrics at query time; a separate PR table maintained on write.
- Why: With 50k+ entries (~150–250k sets) per user, PRs must not scan all sets. Precomputed, indexed columns keep PR reads O(log n). Trade-offs: denormalized columns and slightly slower writes; acceptable because entries are immutable once logged. A maintained PR table was rejected: it adds write-time races and cannot answer arbitrary time-range comparisons. A composite foreign key forcing the copied columns to match the parent entry was also rejected (extra multi-column unique index and 5-column FK for little gain); instead sets take the copied values from the entry row returned by the insert, in a single code path covered by tests.

## 2026-10-08 — Unknown exercise names
- Decision: Logging an exercise that is not in the catalog creates it automatically with no muscle groups. Names are matched on a normalized form (Unicode NFKC, trimmed, lowercased, collapsed spaces), unique in the DB.
- Alternatives: reject with 400.
- Why: Coaches are never blocked; the assignment says muscle group filtering applies "if exercise metadata is available". New exercises get muscle groups once added to the config.

## 2026-10-08 — Idempotency and concurrent writes
- Decision: Enforced in the database with a natural key: UNIQUE `(user_id, exercise_id, performed_at)` on `workout_entries`. Inserts use `INSERT ... ON CONFLICT DO NOTHING`; a duplicate is not re-inserted and the existing entry is returned, flagged as a duplicate in the response.
- Alternatives: `Idempotency-Key` header table; client-generated entry ids; transactions only; overwriting sets on conflict; 409 Conflict.
- Why: Matches the assignment's case ("same user logging same exercise at same time") and is race-free: the unique index decides, not a check-then-insert in code. Retries need nothing extra from the client because they resend the same `date`. Trade-off: two genuinely separate logs of the same exercise at the exact same timestamp collapse into one, which is acceptable because sets of one session belong in one entry.

## 2026-10-08 — Muscle groups
- Decision: Separate tables `muscle_groups (id, slug, name)` and `exercise_muscle_groups (exercise_id, muscle_group_id)`, seeded from a config file (not hardcoded in code).
- Alternatives: `text[]` column on exercises; JSONB metadata.
- Why: A future screen can list muscle groups with display names and let users pick one; foreign keys prevent typos. Performance is the same as an array because the catalog is small; the heavy part of filtered history is the `workout_entries` index.

## 2026-10-08 — Seeding the exercise catalog
- Decision: The seed only initializes data. Muscle groups (by slug), exercises (by normalized name) and exercise–muscle-group pairs are inserted if missing (`ON CONFLICT DO NOTHING`); existing rows are never updated or deleted, so later config edits do not rewrite stored data. The config is validated before anything is written (unknown slugs, duplicate normalized names, exercises without muscle groups) and all inserts run in one transaction.
- Alternatives: config as source of truth that replaces mappings on every run; upserting display names.
- Why: Seeding is for initial content; once data is in the DB it belongs to the running system. Insert-only is idempotent and safe to run on every container start. Trade-off: correcting a mapping already in the DB needs a migration or a manual change, not a config edit.

## 2026-10-08 — Units, decimal math and 1RM
- Decision: A `UnitConverter` provider backed by a registry of factors to kg (`kg: 1`, `lb: 0.45359237`, the exact international pound). Supported units for validation come from the same registry, so adding a unit (e.g. `stone: 6.35029318`) is a one-line change. All arithmetic uses decimal.js. Estimated 1RM uses the Epley formula exactly as specified, `weight × (1 + reps / 30)`, for every set including single-rep sets. Volume is `reps × weight`. The kg weight is rounded to the stored scale (6 decimals) first and volume / 1RM are computed from that rounded value, so the three stored columns always agree; responses round to 2 decimals. The registry constant is the single source for both request validation and the injected converter (no swappable DI token that could drift from validation).
- Alternatives: Prisma.Decimal (couples domain math to Prisma); JS numbers with rounding (float error, against project rules); treating a 1-rep set's 1RM as the lifted weight.
- Why: Exact decimal math avoids float drift in stored and aggregated values. Following the specified formula keeps results predictable for reviewers; trade-off: a 1-rep set estimates slightly above the lifted weight (100 kg × 1 → 103.33 kg).

## 2026-10-08 — Bulk logging
- Decision: `POST /api/v1/users/:userId/workouts` with `{ entries: [{ date, exerciseName, sets: [{ reps, weight, unit }] }] }`, processed synchronously in one transaction. The whole request is validated first; any invalid field rejects the entire request with 400 and nothing is stored (`details` point to e.g. `entries[3].sets[1].weight`). Limits: ≤ 100 entries per request, ≤ 50 sets per entry, reps 1–1000, weight 0–2000 in the sent unit (max 3 decimals), userId `[A-Za-z0-9_-]{1,64}`. Dates must be ISO 8601 with an offset and not in the future (no clock-skew tolerance). Two entries with the same exercise and instant in one request are rejected. Response is 201 if at least one entry was created, 200 if every entry was a duplicate; each entry reports `status: created | duplicate` and its id.
- Alternatives: background processing via a queue; partial success (207); always 201 or 409 on duplicates; tolerance for future timestamps.
- Why: Payloads are small (≤ 5,000 sets), so a synchronous transaction finishes in milliseconds and the coach gets validation errors, duplicates and ids immediately, with history/PRs consistent right away. A queue would add infrastructure (Redis, workers, job status) the assignment does not need; it fits large imports and side effects (PR notifications) at scale. All-or-nothing keeps the client simple and retries are safe thanks to idempotency. 200 vs 201 lets a client tell a no-op retry from a real write. Trade-off of zero future tolerance: a client clock running ahead can get a 400 for "now".

## 2026-10-08 — Workout history
- Decision: `GET /api/v1/users/:userId/workouts` returns entries (newest first, `performed_at DESC, id DESC`) with their sets nested. Filters: `exercise` (case-insensitive partial match on the normalized name; `%`/`_` escaped), `muscleGroup` (slug; unknown slug → 400 listing valid slugs), `from`/`to` (calendar dates `YYYY-MM-DD`, inclusive, compared with the client's `local_date`). `unit` converts every weight (default kg). Keyset pagination with an opaque base64url cursor over `(performed_at, id)`, `limit` default 20, max 100; invalid cursor → 400. No results → 200 with `data: []` and a message. The date filter also adds `performed_at` bounds widened by the maximum allowed offset (±14h) so the `(user_id, performed_at)` index can be used, while `local_date` gives the exact calendar match. Exercise and muscle-group filters are resolved to exercise ids on the catalog first (both must match); when no exercise matches, the empty page is returned without querying history, otherwise history is filtered with `exercise_id = ANY(ids)`. Measured: a filter matching nothing went from 13.8 ms (walking all 50,000 entries) to 0.01 ms.
- Alternatives: datetime range on `performed_at`; keep each set's original unit when `unit` is omitted; a flat list of sets; empty result for an unknown muscle group; OFFSET pagination.
- Why: Coaches think in calendar days ("October"), and `local_date` keeps history consistent with monthly PR comparisons. A single default unit (kg) makes responses uniform. Nesting matches "list workout entries" and keeps a session's sets on one page. A 400 for an unknown muscle group catches typos instead of looking like "no data". Keyset pagination stays O(page) at 50k+ entries, where OFFSET degrades linearly; the opaque cursor lets the ordering change without breaking clients.

## 2026-10-08 — Personal records
- Decision: `GET /api/v1/users/:userId/records?exercise=<name>` (matched on the normalized name; unknown exercise → 404). Returns three PRs, each from a single set: heaviest weight, highest set volume (reps × weight) and best Epley 1RM, with the set's reps/weight, `performedAt`, `localDate`, `entryId` and `setIndex`. Without a range it covers all history; `from`/`to` (calendar dates on `local_date`, inclusive) restrict it. Comparison takes an explicit second range `compareFrom`/`compareTo` and returns that range's PRs plus the difference per metric (`current − compared`, null if either side is missing). When the same value was reached several times, the most recent set is reported. `unit` converts values (default kg). No sets in the range → 200 with null records and a message.
- Alternatives: exercise id in the path; preset periods (`period=month`); earliest achievement on ties.
- Why: Names match how workouts are logged. Explicit ranges support any comparison (week, month, year) and avoid guessing the user's timezone for "this month", which the API does not store. Most recent on ties shows the user still lifts at that level (user's choice). Each PR is a top-1 lookup on the precomputed, indexed set metrics, so it stays fast at 50k+ entries. `difference` is computed from the two values as displayed (converted and rounded to 2 decimals), so it always matches the numbers the client shows; computing it from unrounded values could differ by at most 0.01 and produce e.g. "100.00 vs 100.00, difference 0.01".

## 2026-10-08 — README structure
- Decision: README covers architecture (Mermaid diagrams), setup via `docker compose up`, schema and design decisions, timezone and indexing strategy, trade-offs and scaling. Each decision is summarized in 2–3 lines and links to this file for alternatives. API documentation is the Swagger UI at `/docs` (OpenAPI JSON at `/docs-json`), which the README links to instead of repeating endpoints, payloads and error codes. The performance section is filled after the 50k-row EXPLAIN step.
- Alternatives: full rationale inside the README; an endpoint table, curl examples and an error-code table in the README.
- Why: One source of truth for the API (generated from the DTOs and kept in sync with validation), and a README that reads in about ten minutes. Trade-off (user's choice): the assignment lists API docs as a README item, so the README points reviewers to Swagger explicitly.

## 2026-10-08 — Primary keys: UUIDv7
- Decision: `exercises`, `workout_entries` and `workout_sets` use UUID primary keys generated by PostgreSQL 18's native `uuidv7()` (added in a separate migration; earlier v4 ids stay valid). `muscle_groups` keeps its small integer id. Ordering for history and the cursor is still `(performed_at, id)`: a v7 id reflects when a row was written, not when the workout happened (backfilled or offline-synced workouts are written later), so `id` stays a tie-breaker only.
- Alternatives: random UUIDv4 (`gen_random_uuid()`, the initial default); `bigserial`; v7 generated in the app.
- Why: Same 16-byte storage as v4, but time-ordered ids are appended to the right edge of the primary-key B-tree instead of landing on random pages, which keeps inserts cheap and the index compact as `workout_sets` grows to hundreds of millions of rows. UUIDs (unlike `bigserial`) do not expose row counts and can be generated anywhere if ever needed. Generating them in the database keeps the bulk `INSERT ... SELECT FROM unnest(...)` unchanged.

## 2026-10-08 — Demo and performance seed data
- Decision: A separate, opt-in command (`npm run db:seed:demo`, also runnable inside the container) generates workout history: one `perf-user` with 50,000 entries for the E6 measurements plus 20 smaller demo users. It is not run on container start. Data is generated in Node with a fixed-seed PRNG, reusing the domain code (`UnitConverter`, `computeSetMetrics`) and the repository's bulk inserts, so stored kg/volume/1RM values match what the API would write, and the same catalog config always produces the same data (row ids differ). Insert-only like the catalog seed, and resumable: users that already have their target number of entries are skipped; otherwise the same natural keys are regenerated and `ON CONFLICT DO NOTHING` adds only the missing entries, so a run that died between batches is completed by running it again. The catalog expansion (more muscle groups and exercises) is a separate follow-up.
- Alternatives: seeding on every start or behind an env flag; a single 50k user only; 5 users × 50k; pure SQL with `generate_series`.
- Why: `docker compose up` stays fast and reviewers start from a clean database. Reusing the domain code avoids a second implementation of Epley and rounding that could drift. Deterministic data makes EXPLAIN results reproducible. Small users next to the large one show that queries stay scoped by `user_id`.

## 2026-10-08 — Performance evidence (E6)
- Decision: A reproducible script (`npm run db:explain`) measures the read paths on the seeded `perf-user` (50,000 entries). It calls the real repository methods with a transaction stand-in that wraps their SQL in `EXPLAIN (ANALYZE, BUFFERS)`, so the measured SQL is exactly what the API runs. It also times each endpoint over HTTP (sequential requests after warm-up, p50/p95) against the running app. Results are written to `docs/PERFORMANCE.md`; the README shows a summary table. This step only measures: any index change found necessary is a separate change with before/after numbers.
- Alternatives: hand-run EXPLAIN on copied SQL; EXPLAIN only, no HTTP timing; a load-testing tool (autocannon, k6).
- Why: Copied SQL drifts from the code; generated evidence can be re-run by reviewers. HTTP timing shows the end-to-end cost (Nest pipeline, unit conversion, JSON) next to the database time. Keeping fixes out of the measuring step gives a clean before/after story and one concern per change.

## 2026-10-08 — Architecture: modular monolith refactor
- Decision: Reorganize the code per `docs/ARCHITECTURE_BRIEF.md`: `src/modules/workout` (logging, history, personal records, unit conversion) and `src/modules/exercise` (catalog, muscle groups), each with `controllers/`, `services/`, `repositories/`, `dto/`, `domain/` only where code exists; a small `src/shared/` (errors and the Swagger response decorators used by controllers); `src/infrastructure/` (Prisma, seed and perf scripts, HTTP pipeline and Swagger setup, config, logging). The Swagger decorators were first planned under `infrastructure/http` and moved to `shared/swagger` during step 2: controllers use them, so keeping them in infrastructure would make business modules depend on the HTTP layer. API paths and behavior stay the same. A `TransactionRunner` in infrastructure replaces direct `PrismaService.$transaction` calls in services, because bulk logging spans both modules in one transaction. Only `WorkoutRepository` gets an abstract class (also the DI token) with a `PrismaWorkoutRepository` implementation; the personal-record and exercise repositories stay concrete. `ExerciseModule` keeps exporting its repository rather than adding a pass-through service. Every step must respect SOLID, applied pragmatically (see the brief): single-responsibility layers, extension through data or new implementations, substitutable implementations, narrow abstractions, and services depending on abstractions they own instead of Prisma. Scheduled after `AI_WORKFLOW.md`.
- Alternatives: keep the current flat folders; abstract classes for every repository; an `ExerciseService` as the module's public API; refactor before writing `AI_WORKFLOW.md`.
- Why: Business-capability modules with one internal layout tell the next developer where code goes as the product grows, without enterprise DDD ceremony. The workout repository is the main persistence boundary worth abstracting; the others would add files without a real boundary. A pass-through exercise service adds little while the catalog is small. Writing `AI_WORKFLOW.md` first secures the remaining required deliverable; its file paths are updated after the refactor.
