# Decisions

Decisions made with the user during planning. Feeds the README "design decisions / trade-offs" section.

## 2026-10-07 — ORM
- Decision: Prisma.
- Alternatives: TypeORM (closest to Eloquent, official @nestjs/typeorm), Drizzle (SQL-like, typed).
- Why: Fast setup, generated migrations, strongest type-safety. Heavy aggregation / pagination queries are written as raw SQL with `$queryRaw` tagged templates (bind parameters) for full control over query plans and indexes.

## 2026-10-07 — Database for e2e tests
- Decision: A separate test database (`everfit_test`) on the same Postgres container in docker-compose.
- Alternatives: Testcontainers (fresh container per run).
- Why: Simple and fast, no extra dependency. Trade-off: tests share a long-lived DB, so each test uses its own userId and the suite resets tables before running.

## 2026-10-07 — Startup behavior of `docker compose up`
- Decision: The app container runs `prisma migrate deploy` (and the exercise seed, once it exists) automatically before starting.
- Alternatives: Manual migration/seed commands documented in README.
- Why: The assignment requires setup to work with `docker compose up`; reviewers get a working API with one command. The 50k-entry performance seed stays a separate command.

## 2026-10-07 — API documentation
- Decision: Swagger (OpenAPI) UI at `/docs`, generated from DTOs; README summarizes endpoints and error codes.
- Alternatives: README only.
- Why: Docs stay in sync with validation rules, and the video demo can use Swagger UI.

## 2026-10-08 — Test runner
- Decision: Vitest (+ Supertest for e2e), as generated by NestJS 12.
- Alternatives: Jest (default in NestJS ≤ 11).
- Why: The project is ESM (`"type": "module"`); Jest's ESM support is still experimental and needs extra configuration, while Vitest supports ESM and TypeScript out of the box and is faster. The API is nearly identical to Jest. Known risk: if Nest DI fails in tests due to missing decorator metadata, add the SWC plugin (`unplugin-swc`).

## 2026-10-08 — Environment validation
- Decision: Validate env vars at startup with class-validator / class-transformer via `ConfigModule.forRoot({ validate })`; the app fails fast with a clear message.
- Alternatives: Zod, Joi.
- Why: class-validator is needed for request DTOs anyway, so one validation library serves the whole app with no extra dependency.

## 2026-10-08 — Logging
- Decision: Structured logging with nestjs-pino. JSON output in production/Docker; pino-pretty (dev dependency) for local development. Every HTTP request is logged once (method, url, status, response time, requestId) without request/response bodies. Request id comes from the `x-request-id` header or is generated (UUID) and echoed back.
- Alternatives: JSON everywhere; logging bodies; logging errors only.
- Why: JSON logs are machine-parseable for log aggregation; pretty logs keep local work and the video demo readable. Not logging bodies keeps log volume low (bulk requests can be large) and avoids leaking user data.
- Note: The request URL is logged with its query string. Query params here are filters (exercise name, date range, unit), not sensitive data, and they are needed to debug slow or failing list queries. Revisit if sensitive params are ever added.
- Note: `NODE_ENV` defaults to `production`, so a missing value never tries to load dev-only tooling (pino-pretty is a dev dependency).
